# Zimlet documentation: sources, gaps and build order

This file belongs to the [Zimlet documentation plan](./zimlet-documentation-plan.md). It holds the known gaps that feed the guide and the build order with the status of each phase. Page statuses are in section 1 of the plan. Open claims are in [zimlet-documentation-claims.md](./zimlet-documentation-claims.md).

## Known gaps that feed the guide

Published in P38 in user-friendly form. Only unresolved gaps are listed. When a gap is answered, remove it and write the answer into the page, plan or reference file it affects. Gap numbers are not reused or renumbered.

**A. Missing information (nothing in the source files)**

2. The Zimbra release to `zm-x-web` version mapping is not documented, though it is needed to choose `--zimbraXVersion`. The template and the guide use `^4.0.0`, the host is 4.50.0. Only the About-dialog lookup is documented.
3. Sideloader: how to obtain, build and deploy it, whether it is pre-installed, and which COS or users need it are not documented.
4. Update, redeploy, undeploy and rollback behaviour of `zmzimletctl` for a deployed Zimlet is not described.
5. Windows: package scripts use `$npm_package_name` (POSIX shell syntax); behaviour on cmd or PowerShell is untested (inferred, to confirm).
6. Per-slot details for each extension point are not researched (all `unclassified`). P34 ships a factual index now. Security guidance (P24) is researched from code and reviewed by Engineering after all pages are drafted.
7. Distribution for non-Zimbra developers (publishing, signing, licensing) is not documented.
8. There is no versioning policy for Zimlets (Zimlet semver against the host compatibility range).
9. The Classic to Modern capability list is incomplete. The sources say the Classic compat bridge is disabled and list a few differences, but there is no authoritative inventory. Engineering reviews P39 after all pages are drafted; comparing the Classic Zimlet repositories with the Modern slot catalog could help.
10. API reference depth: the available server API endpoints and the `zimbraBatchClient` operations are not described; the guide shows the `fetch` pattern and points to host source folders. Hooks and exports are documented only as far as verified in `shims.js` and the host source.

**B. Known defects and staleness**

Tracked in [zimlet-known-issues.md](../../../zm-modern-zimlets/.agents/reference/zimlet-known-issues.md). Do not copy items here; update that file instead.

Phase status values: `Not started` · `In progress` · `Done`. A phase is `Done` when every page it lists is at least `Drafted` and its other work (spike, inventories) is finished. Update the status in the same change that finishes the work. To check a page, find its phase in the "Pages" column; its dependencies are the phases in that row's "Depends on" column, and they are satisfied only when those phases are `Done`.

**After all pages are drafted** (outside the phases; not a dependency of any phase or page): P24 and P39 are written last and reviewed by Engineering. They are not listed in any phase.

If a page's dependencies are not `Done`, an agent stops and asks the user. It continues only after the user confirms, and it records nothing in this file about that decision. An agent sets a phase to `Done` only when the page work and the non-page work are both finished.
