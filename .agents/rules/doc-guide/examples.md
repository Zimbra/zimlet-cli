# Rules for examples in the Zimlet documentation

Section 4 of the writing rules in [write-doc.md](../write-doc.md). Read it in full together with that file.

## 4. Examples

- Give a working example for every topic that tells the reader to write code or configuration, and for every slot or extension point page. Registering a slot always needs one.
- When writing a complete, runnable Zimlet example, use the [Zimlet creation workflow](../../workflow/create-zimlet.md).
- Examples must follow [authoring.md](../authoring.md): `createElement` imported from `preact` in JSX files, only shimmed imports, plugins registered inside `init()`, and `en_US.json` structure for strings. Also follow the coding style of the default template: tab indentation (the `indent_style = tab` rule of its `.editorconfig`), single quotes, a line width of 100 (its `.prettierrc`), and `createElement` as the JSX pragma. Prettier takes the tab setting from `.editorconfig`, so a file that is linted without an `.editorconfig` next to it or above it reports tabs as errors; this is not a defect of the example. Packaging and `config_template.xml` examples must follow [packaging-deployment.md](../packaging-deployment.md).
- Style tokens in `.less` examples: use the style tokens of `zm-x-ui` instead of fixed values wherever a token exists, for spacing (`--spacing-*`), font sizes (`--font-size-*`), line heights, radii (`--radius-*`), icon sizes (`--icon-size-*`), colours and borders. Take the token names only from the `zm-x-ui` files, and check each name there before you use it. Follow [shared-styles.adoc](../../../documentation/modules/ROOT/pages/go-deeper/styling/shared-styles.adoc) for how to use them:
  - [`css-variables.css`](../../../../zm-x-ui/css-variables.css) has every token as a CSS variable, with its light and dark values. Read it for the exact name, and write `var(--spacing-md)` in the example. Do not import it.
  - [`variables.less`](../../../../zm-x-ui/variables.less) has the same tokens as Less variables, grouped by area (layout sizes, grays, brand colours, borders, forms, headings, icon sizes and spacing). Use them only in an example that imports `refs.less` from `@zimbra/x-ui`, as the page describes.
  - [`palette.css`](../../../../zm-x-ui/palette.css) has the brand colour scales, such as `--brand-primary-50` to `--brand-primary-900`.
  - [`helpers.less`](../../../../zm-x-ui/helpers.less) has the mixins: screen sizes, layout (`.fit()`, `.fill()`), scrolling (`.scroll()`), list items (`.listItem()`), toolbar sizes (`.toolbarHeight()`) and popovers (`.popover()`). Use a mixin instead of repeating its rules. Import it with `(reference)` only, as the page describes.
  - Add a short comment with the value only on a token whose value its name does not show, for example `// 1.1`. Leave out the comment on tokens with a clear name, such as `--spacing-md`, `--font-size-base` and colour tokens.
  - Do not import `index.less`, which adds the Roboto font files to the build.
  - Use a token only when it gives the same value as the fixed one (`16px` becomes `var(--spacing-md)`, `14px` becomes `var(--font-size-base)`). The example must look the same after the change. If no token has the same value, keep the fixed value: do not pick the nearest token, and do not change a colour, a size or an opacity to fit one. Allow one level of `calc()` on a token (`calc(var(--spacing-md) + var(--spacing-xs))`) when it gives the same value. If it needs more than one level, keep the fixed value. Keep a fixed value where the files have no token for it, such as `font-weight` (only `--headings-font-weight` exists, at 300) and a `1px` border width.
- Draw an icon that your own component renders with the `Icon` component of `@zimbra-client/blocks`, not with the `lucide-preact` component directly. Import the icon from `lucide-preact` and pass it as `name`, for example `<Icon name={StarIcon} size="sm" />`. Choose the `size` that fits the text or control next to it: `xs` (12 px) for a mark inside small text, `sm` (16 px) beside body text or inside a button, `smd` (20 px) and `md` (24 px) for toolbar and menu icons, `lg` (32 px) and `xl` (40 px) for large artwork. Do not set a pixel size (`size={14}`) or a fixed `width`. A host component that has an `icon` prop (`Button`, `MenuItem`, `ActionButton`, `ActionMenuItem`) takes the `lucide-preact` component itself and sizes it, so pass it as it is. Check the sizes in `components/icon` of the blocks library before you write them.
- Redux in examples: in a component or a hook, read the state with `useSelector` and send actions with `useDispatch`, both from `react-redux`. Use `store.dispatch` and `store.getState` only where no component renders, such as `init()`, an event listener or a plain function, and say why in the text. Never pass the whole `store` or `context` down to a child component or a hook. Read what the child needs in the handler or in `init()` (an action creator such as `addModal` or `notify`, a client, a value) and pass only that.
- Examples are complete and copy-pasteable, with imports and the default export. If a snippet could not be run, record it in [open claims](../../plans/zimlet-documentation-claims.md) as described in section 2.
- Lint every example file before you add it under `modules/ROOT/examples/`. Run the Lint steps of the [zimlet-doc-verify](../../skills/zimlet-doc-verify/SKILL.md) skill on it. They use the ESLint config of the default template (`eslint.config.mjs`, with `@zimbra/eslint-config`), the one a reader's new project has, so an example that passes also passes there. Fix every problem it reports, either by hand or with ESLint `--fix` on a scratch copy that you then copy back, and lint again until ESLint exits 0 with no problems. Add the file to the page only after it passes. A folder example is linted the same way, as a whole. If a problem cannot be fixed, do not add the example; tell the user why.
- Keep every JS, JSX, JSON, XML and Less example longer than two lines in its own file under `modules/ROOT/examples/<topic>/` and include the whole file: `[source,<language>]` followed by `include::example$<topic>/<path>[]`. Do not show part of a file with `tag::`/`end::` comments or `tags=`, because a snippet hides the imports, the default export and the surrounding code the reader needs. Keep tag comments out of example files, since a whole-file include prints them. Say in the text what the example does, before the listings.
- An example that spans several files of a Zimlet keeps the files' relative paths. Store each file at the same path it has in the Zimlet, under `examples/<topic>/` (for example `index.js`, `components/Button/index.js`, `components/Button/style.less`). Show each file as its own listing with a block title that is its path (`.components/Button/index.js`), so the reader sees where each file goes. Start with the entry file (`index.js`). Keep the set of files as small as the use case needs, following the one-use-case rule below.
- Inline code is allowed only for one or two lines (an import, one call, a config key) and for short shell commands in numbered steps. Use `[source,js]` or `[source,sh]` and always set the language.
- Take the project structure only from the [default template](../../reference/authoring.md#starting-from-the-default-template) (`template/` in the sibling `zm-x-zimlet-template-default` checkout): the folder layout, `package.json` (scripts, dependencies, devDependencies), the lint and format setup (`eslint.config.mjs`, `.prettierrc`, `.editorconfig`), `zimlet.config.js`, the commit hooks and the README. Do not take any of these from a monorepo Zimlet, and do not describe a monorepo-only setup (such as its `security:audit` script or its root lint config) as part of a Zimlet's structure. Everything below is about code examples.
- Find the Zimlet to take a code example from in this order, and stop at the first source that covers the topic:
  1. The [default template](../../reference/authoring.md#starting-from-the-default-template) (`template/` in the sibling `zm-x-zimlet-template-default` checkout). It covers the factory and `init()`, the Email tab (`slot::email-tab-item`) and its route (`slot::routes` with `useClientConfig`), localization (`withIntl`, `Text`, `en_US.json`), CSS Modules with `@zimbra/x-ui`, `zimlet.config.js` and the `package.json` scripts.
  2. [zimlet-examples.md](../../../../zm-modern-zimlets/.agents/reference/zimlet-examples.md) in `zm-modern-zimlets`: its curated list first, then, if the topic is not there, its registration patterns and their [data file](../../../../zm-modern-zimlets/.agents/context/zimlet-patterns.yml).
  3. The Zimlet sources in the sibling repositories, if neither has it.

  Inspect the relevant source, then create a simple, focused example for the topic using only the necessary details. Do not copy a whole Zimlet or template file, and do not name the template or a real Zimlet as the example's source.
- Choose the slot (or other registration key) that fits the use case, as a user would expect to find it. A toggle for a view setting belongs in a menu, not above the message text. Do not reuse a slot from another example by default, and do not pick one because it is easy. Look for the slot in the catalog [zimlet-slots.yml](../../../../zm-x-web/.agents/zimlet/context/zimlet-slots.yml), and look at how an existing Zimlet fills a similar slot ([zimlet-examples.md](../../../../zm-modern-zimlets/.agents/reference/zimlet-examples.md)), including the component that it renders. Confirm that the slot name exists. If an example only shows an API call and its UI does not matter, use a handler that shows nothing (`() => null`) or a key of your own, and do not invent a placement.
- Choose a use case that needs the feature. Ask what the reader would use instead. If an existing, simpler API already gives the same result (for example, listening to `zimlets-initialized` instead of a custom event that only says that loading has finished), the example is not a real use case, and you must pick another. The feature must carry something that the reader cannot get another way, such as a user choice that one Zimlet owns, the result of a lookup that another Zimlet should not repeat, or a state that only the sender computes. Check this before you write the example, and state the use case in one sentence in the text.
- Show the real use case. If the feature connects two or more Zimlets (for example an event that one Zimlet sends and another receives), the example has one listing for each Zimlet, with a block title that names its role (`Sender: src/index.js`). A single Zimlet that talks to itself shows the call, not the use. Say in the text that the reader installs both, and state any timing the use case depends on.
- An example shows one use case with the least code that conveys it. (The recipes of `build-by-goal/` follow "Build by goal recipes" below instead.) Leave out features, helper components, styling, localization and business logic that the topic does not need. Use neutral names (`Greeting`, `my-zimlet`) and do not tie the example to a product feature, so the reader can adapt it to their own case. If you cannot say in one sentence what the example demonstrates, it is too big or too specific: cut it or split it.
- Vary the examples. Two entries or two pages do not show the same example. Use a different API, hook, component, slot or value for each, so that every example shows its own entry and not a copy of a neighbour. Before you add an example, check the page and the pages next to it for the same code, and change yours when it repeats. A deliberate repeat, such as `const { plugins } = context;` as the first line of a context example, does not count.
- An example must demonstrate the use case of every API, hook, helper or constant that the page names for it. Simple is fine; printing the value is not enough. Show the reader why they would call it and what they do with the result: use a returned value to decide what to render or do (for example, compare `getPlatformType()` with `PLATFORM_TYPES` and show different content), and put a returned field into real content (for example, `data.accountInfo.name` inside a welcome string) instead of printing it bare. If an API appears in the example only to be imported or displayed, drop it from the example or add the behavior that shows its purpose. Check the result against the API's real return values (read its source) and say in the text what the example does with each one.
- Except in the recipes of `build-by-goal/` (see "Build by goal recipes" below), visible text in an example is always a label held in a constant, never literal text in the JSX and never `<Text id>` with `withIntl` and `en_US.json`. Declare the constant at the top of the file, after the imports, in upper case (`const GREETING_LABEL = 'Hello';`), and render it as `{GREETING_LABEL}`. Put a comment above the constant that says to use localization instead, for example `// Use localization for visible text in a real Zimlet.`. This keeps the example short and passes the `preact-i18n/no-text-as-children` lint rule of the default template. Do not add a `NOTE` after the example for this; the comment is the disclosure. Where the example has no visible text, add neither the constant nor a comment about localization (no "this example needs no translation"). Leave the comment out on a page that teaches the full approach (`go-deeper/localization.adoc` and the recipes that use `<Text>`), where the text comes from `en_US.json`. Any other part of [authoring.md](../authoring.md) that an example leaves out for simplicity is disclosed in a short `NOTE` right after the first example on the page that has it, with its consequence and an `xref:` to the page that owns the full approach (see section 1 of [zimlet-documentation-plan.md](../../plans/zimlet-documentation-plan.md); if that page is not written yet, link it by file name with no `#anchor`, as [write-doc.md](../write-doc.md) describes). Say that the build or compile fails only when you have checked that it does.
- Never simplify away something that makes the Zimlet fail at run time or fail to build: the `createElement` import, shimmed-only imports, registering inside `init()`. An example that leaves these out does not work, so keep them even if it makes the example longer.
- Confirm the example against the real pattern (the slot name, the props, the imports).
- Placeholders in examples are marked `<like-this>`; never use real accounts, hostnames or tokens.
- Any web address in an example (a link, a base URL, a service address) uses `https://zimbra.github.io/zimlet-cli` as its base, with a path added to it, for example `https://zimbra.github.io/zimlet-cli/meet/<id>`. Do not use any other host, not even a reserved one such as `example.com`. State in the text that the address is a placeholder when the reader must replace it.

A slot registration example looks like this, kept in `examples/slots/register-slot.js` and included in the page:

```js
import { createElement } from 'preact';

export default function Zimlet(context) {
	const { plugins } = context;
	return {
		init() {
			plugins.register('slot::<slot-name>', props => <Greeting {...props} />);
		}
	};
}
```

### Build by goal recipes

These rules apply to every example of a page under `build-by-goal/` (P12.2 to P12.6, the slot recipes P12.1.1 to P12.1.12 and the children of P12.3). They replace the "least code" and "visible text as a constant" rules above for those pages. The rest of this section 4 still applies.

- **A real use case.** Each recipe has one example Zimlet that does something a partner would ship, at the quality of an active Zimlet in `zm-modern-zimlets`: it has a purpose, a user-visible result and the handling the feature needs. A demo that only prints a value or renders a greeting is not enough. Find the closest active Zimlet through [zimlet-examples.md](../../../../zm-modern-zimlets/.agents/reference/zimlet-examples.md) and its registration patterns. Inspect how it splits its code, then write an original example of the same kind and a smaller size. Do not copy a Zimlet and do not name it as the source. State the use case in one sentence in the text.
- **Several files, never one.** Do not put the factory, the components, the data access and the styles in one file. Keep `index.js` for the factory and the registrations in `init()`. Give each component its own folder with its `style.less` (`components/<name>/index.js`, `components/<name>/style.less`). Put hooks, helpers, API calls and constants in their own files (`hooks/`, `api/`, `constants.js`). Put strings in `intl/en_US.json`. Follow the layout of the default template. Each file has one job and is its own listing, with its relative path as the block title and the entry file first, as the multi-file rule above says.
- **What the use case needs.** Include the components, styles, helpers and strings that the use case needs, as a real Zimlet has them, and nothing it does not need. Keep neutral names (`my-zimlet`), so the reader can adapt the example.
- **Component and props sections.** Explain a component that the example uses with a short "Without it" and "With it" pair, then list only the props that the example uses. Give each prop one short line: what it sets and, if the example does not use the default, the value it uses. List a prop and its partner as separate entries when they do different jobs (`href` and `isExternal`). Do not describe how the component works inside (the attributes it sets, the elements it renders, what it does by itself). Send the reader to the reference page for the rest of the props.
- **Visible text.** Use `<Text>` with `withIntl` and `en_US.json`, as `go-deeper/localization.adoc` teaches, instead of the label constant. Link to the localization page for the full approach, and add no comment about localization.
- **Verified as a whole.** Lint every file, and build the whole example in a scratch Zimlet with the [zimlet-doc-verify](../../skills/zimlet-doc-verify/SKILL.md) skill. Give the recipe its verification checklist. Behaviour that shows only in a live Modern UI stays unverified until the user has confirmed it (section 7 of [claims.md](./claims.md)); a stub-host check is not proof of rendering.

### Common slot patterns

- Take the use cases, the Zimlets that implement them and the example to adapt from the sources in the order given in section 4 above. Do not invent a pattern that is in none of them.
- Document slots by use case as well as by name. A "Common patterns" section shows, for each use case (for example add content to a screen, add a menu item or action, add a settings page, add a tab and screen), the slot to use, a complete registration example in `examples/slots/<use-case>.js`, and a link to the slot's catalog entry.
- Every pattern example follows [authoring.md](../authoring.md) and the same rules as any slot example above.

### Calling an API in examples

- Follow the [API calling guidance](../../reference/authoring.md#7-api-calling) to choose a suitable method. Leave GraphQL and Apollo out of the guide, as the rule in [write-doc.md](../write-doc.md) section 2 says: no custom GraphQL operations, no `getApolloClient()`, no `@apollo/client`, no GraphQL or Apollo dependencies. If an example needs data that a GraphQL operation provides, use a ready-made host hook. This restriction applies to documentation examples, not to Zimlet implementation.
