= React to app events

This recipe builds a xref:reference/glossary.adoc#zimlet[Zimlet] that runs code when the user sends a message or logs out. The action waits until the code has finished. The example asks for confirmation before a message goes to an address outside your organization. It saves the domains that the user approved when the user logs out. Use it when your Zimlet must check, delay or stop an action of the xref:reference/glossary.adoc#modern-ui[Modern UI], such as sending a message or logging out.

[#what-you-will-learn]
== What you will learn

You learn how to:

* Listen to `ONBEFORESEND` to stop or continue the send.
* Listen to `LOGOUT` to finish work before logout.
* Show a dialog with `addModal` and `removeModal`.
* Remove a listener.

[#before-you-start]
== Before you start

* Follow xref:build-by-goal.adoc#before-every-recipe[Required reading before every recipe].
* Knowledge of the app events and of the two kinds of listener, from xref:go-deeper/app-events.adoc[App events]. The xref:go-deeper/app-events.adoc#sync-or-async[choice between a synchronous and an asynchronous listener] decides how your Zimlet can stop an action.

[#choose-the-events]
== Choose the events

The recipe uses two events. Each one needs an asynchronous listener, because the Modern UI continues only when the promise of the listener is resolved.

`ONBEFORESEND`::
The user chooses *Send*. The listener receives `{ message }` and decides whether the send goes on. It resolves to let the message go, and rejects to stop it.

`LOGOUT`::
The user chooses to log out. The listener receives `null`. It does its work and resolves, and the Modern UI then logs the user out.

An event is the right tool when the Zimlet reacts to something the user does and the action must wait for the answer. If you only need to change what a message shows, use a message processor, as xref:build-by-goal/recipe-message-processing.adoc[Transform messages] shows.

[#keep-the-approved-domains]
== Keep the approved domains

When the user confirms a send, the Zimlet remembers the domains of the recipients and does not ask for them again. The set lives in memory, and a flag tells whether a domain was added since the last save. Only this Zimlet knows that state, which is why an event is the right tool: the Modern UI cannot save it for you at logout.

[#ask-before-sending]
== Ask before a message is sent

The listener of `ONBEFORESEND` collects the addresses in `to`, `cc` and `bcc` that are outside your organization and not yet approved. With none, it resolves at once and the user sees nothing. Otherwise it opens a dialog and returns a promise that the user's answer settles.

The send waits while the dialog is open. The two answers end it differently:

* *Send anyway* approves the domains and resolves the promise. The Modern UI sends the message.
* *Don't send* rejects the promise. The Modern UI does not send the message, and it stays open in the composer. The Modern UI writes the rejection to the browser console and shows nothing to the user, so the dialog is the explanation.

Closing the dialog with the close button also counts as *Don't send*.

[#dialogs-with-addmodal]
=== Show and close a dialog

A listener has no component of its own, so it shows a dialog with the `addModal` action of the Zimlet state. `addModal({ id, modal })` shows the element that you pass, and `removeModal({ id })` closes it. Both come from `context.store.zimletRedux.actions.zimlets`. A hook such as `useDispatch` works only in a component, so the listener sends the actions with `store.dispatch`. See xref:reference/context/store/zimlet-redux/actions.adoc#add-modal[addModal] and xref:reference/context/store/zimlet-redux/actions.adoc#remove-modal[removeModal] for every detail.

Choose an `id` that is yours, as the example does. Close the dialog before you resolve or reject, so that it never stays open after the action goes on. `removeModal` closes every dialog that Zimlets added, so do not call it while a dialog of another Zimlet must stay open.

The example uses these props:

`title`::
The heading of the dialog. Pass a `Text` element.

`acceptText` and `rejectText`::
The ids of the texts for the two buttons. They default to `buttons.yes` and `buttons.no`.

`cancelButton`::
Shows a third button, *Cancel*, when it is not `false`. It defaults to `true`. The example sets it to `false`, because *Don't send* already stops the message.

`onResult`::
A function that the dialog calls with `true` for the accept button, `false` for the reject button and `null` for the close button.

The Modern UI draws the dialog outside your Zimlet, so wrap the component with `withIntl`, as xref:go-deeper/localization.adoc[Localization] describes. Without it, `Text` cannot find the texts of your Zimlet.

[#save-on-logout]
== Save before the user logs out

The listener of `LOGOUT` writes the approved domains to the server, and only when a domain was added in this session. While the request runs, it shows a dialog, so the user sees why logout takes a moment. It resolves when the request ends, and the Modern UI logs the user out.

The listener never rejects. A failed save goes to the browser console, and the user still logs out. A rejection would keep the user logged in and show no reason. Reject only when stopping the logout is the point of your Zimlet.

The user must log out for the save to run. Closing the browser tab does not emit `LOGOUT`, so the domains approved in that session are lost.

[#remove-the-listeners]
== Remove a listener

The example needs both listeners for the whole session, so it never removes them. Remove a listener when the code that needs it goes away. Call `off` with the same event and the same function that you gave to `on`, which is why `index.js` keeps each listener in a variable.

[source,js]
----
zimletEventEmitter.off(ZIMBRA_ZIMLET_EVENTS.ONBEFORESEND, checkRecipients);
----

`off` throws an error when the event has no listener left, so call it once for each listener. See xref:go-deeper/app-events.adoc#remove-a-listener[Remove a listener] for the rules.

[#expected-result]
== Expected result

* A message to an unapproved address outside `INTERNAL_DOMAIN` waits for the user's answer.
* *Send anyway* sends the message and remembers its domains. *Don't send* keeps the message in the composer.
* A message to your own domain, or to an approved domain, is sent with no dialog.
* At logout, the Zimlet saves the approved domains if it added any, and the user is then logged out.

[#if-it-did-not-work]
== If it didn't work

No dialog opens and the message is sent.::
* Cause: The Zimlet is not running, or the recipient is in `INTERNAL_DOMAIN`. Or the Zimlet approved the domain in this session or an earlier one.
* Fix: Check that the sideloader shows *Running*. Send to a domain that is not `INTERNAL_DOMAIN` and that you have not approved. Use the `ZIMBRA_ZIMLET_EVENTS` constant, because a misspelled event name adds a listener that the Modern UI never calls and shows no error.

Choosing *Send* does nothing, and no dialog opens.::
* Cause: A listener threw an error, or an asynchronous listener did not return a promise. The Modern UI then stops the send and writes the error to the browser console.
* Fix: Open the browser console, as xref:run-package-deploy/run-and-debug.adoc#browser-console[Run and debug] describes, and read the error. Return a promise on every path of the listener.

The user sees two dialogs one after the other.::
* Cause: The Zimlet was loaded twice without a page reload, so two listeners are active.
* Fix: Reload the Modern UI page and load the Zimlet once.

The domains are asked for again after the next login.::
* Cause: The user closed the browser instead of logging out, or the save failed. The browser console shows the error of a failed save.
* Fix: Log out with the account menu, and read the console if the problem stays.
