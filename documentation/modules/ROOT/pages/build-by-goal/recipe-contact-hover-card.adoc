= Enhance contact cards

This recipe keeps a personal VIP list. A star appears next to every VIP address in a message and in the composer. A link in the card that opens over an address adds the address to the list or removes it. The details of a contact in Contacts have the same link, and a star in front of it for a VIP. Use it when a feature must mark an address wherever it shows and let the user change the mark from the address itself. The list belongs to one user and is saved on the server. The handlers of a xref:reference/glossary.adoc#zimlet[Zimlet], one for the star and one for each card, share it in the xref:reference/glossary.adoc#modern-ui[Modern UI].

[#what-you-will-learn]
== What you will learn

* Add a link to the contact card with `contact-hover-card-details`.
* Add the same link to the details of a contact with `contact-card-item`.
* Add a mark next to an address with `address-pill`.
* Share state between handlers with Redux.
* Save the list in mailbox metadata.

[#before-you-start]
== Before you start

* Follow xref:build-by-goal.adoc#before-every-recipe[Required reading before every recipe].

[#choose-the-slot]
== Choose the slot

The mark must show next to an address and in the cards that show it. Four slots belong to an address, and the example fills three of them.

[#the-slots]
=== The slots

`slot::contact-hover-card-details`::
In the card that opens when the user rests the pointer on an address for about a second. The slot is in the column of details, below the email address and the phone number.

`slot::contact-card-item`::
In the details of a contact in Contacts, below the phone numbers. It shows when the user selects a contact in the list.

`slot::address-pill`::
In front of the name of an address in the sender and recipient lines of an open message and of an event invitation. It is also inside the pills of the composer.

Look up each slot in the xref:reference/slots.adoc[slot index].

[#other-slots]
=== Other slots

`slot::contact-input-token:button-inner-content`::
Inside the pills of the composer only, in front of the name. Choose it instead of `address-pill` when the mark must not show in a message.

Register one handler for one mark. The composer renders both `address-pill` and `contact-input-token:button-inner-content`, so a Zimlet that registers the same mark for both shows it twice there.

[#choose-where-to-save-the-list]
== Choose where to save the list

The example saves the list in xref:go-deeper/server-data/metadata.adoc[mailbox metadata]. Your code writes the list when the user selects the link. No administrator sets a default for it, and no Settings section edits it. That is the case for which we can use metadata. See xref:go-deeper/server-data.adoc#when-to-store-which[When to use which method].

You can also keep the list as a user value of xref:go-deeper/server-data/zimlet-configuration.adoc[Zimlet configuration]. Save it with a `ModifyProperties` request through the batch client, and load it from the account data. The state, the hooks and the components stay the same. Only the code in `api/vips.js` that saves and loads the list changes.

[#read-and-change-the-list]
== Read and change the list

Two hooks give the components what they need. `useIsVip` tells whether an address is in the list. Every star and every card that shows the address updates when the list changes.

`useToggleVip` adds the address or removes it. It reads the list with `useSelector` and changes it with `useDispatch`. The component renders again whenever the list changes, so each change starts from the current list. The state changes only after the server has saved the list. A failed save shows a notification, as xref:build-by-goal/recipe-mail-action-menu.adoc#notify[The notify action] describes, and leaves the list as it was. The link is off until the list has loaded and while a save runs. A click cannot replace a list that has not arrived.

[#build-the-star-and-the-link]
== Build the star and the link

`VipMark` draws the star for a VIP and nothing for any other address. The star is an icon with a text label, so that a screen reader says what it means. `VipButton` is the link in the card. Its text says what a click does: *Add to VIP list* or *Remove from VIP list*. `VipDetails` puts the two side by side in the details of a contact, so a VIP shows the star in front of the link.

`VipMark` draws the star with `Icon` from `@zimbra-client/blocks`, and not with the `lucide-preact` component directly. Without `Icon`, you set the pixel size of every icon yourself. With it, the icon takes a named size, so it matches the other icons of the Modern UI. The example uses these props:

`name`::
The icon component, here `StarIcon` from `lucide-preact`. The build copies `lucide-preact` into your Zimlet, as xref:fundamentals/shared-libraries.adoc[Shared libraries] explains.

`size`::
`sm`, which is 16 px and suits a mark beside text. The other sizes are `xs` (12 px), `smd` (20 px), `md` (24 px), `lg` (32 px) and `xl` (40 px).

`fill`::
`currentColor`, so that the star is filled with the colour of the text. `Icon` passes it on to the icon.

The link is a `Button` in the style of a link, as xref:build-by-goal/recipe-appointment-field.adoc#button-as-link[The Button as a link] describes. xref:build-by-goal/recipe-server-data.adoc#button[The Button component] explains the component. Both components load their texts with `withIntl`.

[#register-the-handlers]
== Register the handlers

In `init()`, add the state first, then register the handlers and start to load the list. The star needs only the props of its slot, so the handler is the component. The card handler also needs the batch client and the `notify` action, so it passes only those on, not the whole store. One function serves both card slots.

Each slot passes the address as the xref:fundamentals/extending-the-ui.adoc#props-and-payload[prop] `email`. `contact-hover-card-details` and `contact-card-item` also pass `contact`, the saved contact of the address. In the hover card, `contact` is an empty object while the contact loads and when the address is not a saved contact. The example does not use it.

`contact-card-item` passes the first address of the plain *Email* field of the contact. A contact that has only a work or home address passes none, so the handler of the card slots draws nothing when `email` is empty.

[#expected-result]
== Expected result

* The card of every address has a link that adds the address to the VIP list or removes it.
* The details of a contact that has an email address have the same link.
* A VIP address shows a star in a message and in the composer. An address that is not a VIP shows none.
* The list is the same after a reload, because the server keeps it.

[#if-it-did-not-work]
== If it didn't work

The star and the link do not show.::
* Cause: The Zimlet is not loaded, or the handlers are registered under other keys. The Modern UI does not check keys, so a misspelled key adds nothing and shows no error.
* Fix: Check that the sideloader shows the Zimlet as *Running*. Check that the keys are `slot::address-pill` and `slot::contact-hover-card-details`, and that you register in `init()`. Reload the page.

The link does not respond.::
* Cause: The list has not loaded. The read of the list failed, or the reducer was added under another name than the one that the hooks read.
* Fix: Open the browser console and look for the error that `init()` logged. Check that `NAMESPACE` is the same in `index.js` and in the hooks, and that the section name starts with `zwc:`.

A notification says that the list could not be saved.::
* Cause: The request to the server failed.
* Fix: Open the network tab of the browser and look at the `ModifyMailboxMetadata` request. A section name without the `zwc:` prefix is rejected.

The star shows twice in the composer.::
* Cause: The same mark is registered for `address-pill` and for `contact-input-token:button-inner-content`. The composer renders both.
* Fix: Register the mark for one of them.
