= Add a control to a built-in settings page

This recipe adds one control to a page that the Settings dialog of the xref:reference/glossary.adoc#modern-ui[Modern UI] already has. The example adds a *Closing phrase* field beside the built-in options on the Writing Email page. The dialog saves it through `modifyProps`. See xref:go-deeper/server-data/zimlet-configuration.adoc#user-values[Let users save their own value] for how the Settings dialog saves it. Use this recipe when a single option of your xref:reference/glossary.adoc#zimlet[Zimlet] belongs with settings that users already know. Build a section of your own instead when the Zimlet has several options, as xref:build-by-goal/recipe-settings/new-section.adoc[Add a section to the Settings dialog] describes.

[#what-you-will-learn]
== What you will learn

* Pick the slot of a built-in settings page.
* Register the `settings` key with `fields` only.
* Report a change with `onFieldChange`.
* Show help text with `HelpTooltip`.

[#choose-the-slot]
== Choose the slot

A built-in page draws the controls of Zimlets in a slot that it names. The slot decides where the control appears and what it receives. Pick the slot of the page that your option belongs to, and of the place on that page. The example fills the slot that ends the Writing Email page.

[#the-slot]
=== The slot

`slot::writting-email-additional-settings`::
The end of the Writing Email page, after the last built-in option. The name is spelled with two `t` in the Modern UI, so use it as written. Look up the slots in the xref:reference/slots.adoc[slot index].

[#add-the-control]
== Add the control

The page creates your component with `value` and `onFieldChange`. `value` holds the values of every field of the page, including the built-in ones, so read only your own by its name. The control reads the value on every render and reports each change at once, so the field always shows what the dialog will save.

Only the first three slots of the table pass `value` and `onFieldChange`, so only they can hold a control whose value the dialog saves. A control in the other two slots can show content or do its own work, and cannot report a value to the dialog.

[#text-input]
=== The TextInput component

The example draws the field with `TextInput`, as xref:build-by-goal/recipe-settings/new-section.adoc#text-input[The TextInput component] describes. Here it needs `id`, `value` and `onInput`. It also gets `maxLength`, which goes to the `input` element and stops the user from typing more characters than the limit.

[#help-tooltip]
=== The HelpTooltip component

`HelpTooltip` shows a question mark button that opens a short help text. It comes from `@zimbra-client/components`. Choose it for an explanation that the label alone cannot give, in the way that the built-in settings do.

*Without it:* you write the explanation as a line of text under the field. That does not look like the other rows and makes the page longer.

*With it:* put the help in the children of a `HelpTooltip`, next to the label.

[source,js]
----
<HelpTooltip position="right" customStyle={style.tooltip}>
	<p class={style.tooltipTitle}>
		<Text id="my-zimlet.closingPhraseLabel" />
	</p>
	<p>
		<Text id="my-zimlet.closingPhraseTooltip" />
	</p>
</HelpTooltip>
----

The example uses two props:

`position`::
Where the tooltip opens. The default is `left`. The example uses `right`.

`customStyle`::
A class for the tooltip. The example sets its width.

The children are the content of the tooltip. Look up the rest in xref:reference/shims/components/dialogs-and-feedback.adoc[Dialogs and feedback].

[#register-the-control]
== Register the control

Register two handlers in `init()`. The slot handler draws the control. The `settings` handler adds the field. Its `id` is the id of the built-in page, and it has no `title` or `component`. The dialog merges `fields` into the fields of that page. If you add a `title` or a `component`, the dialog ignores them, because the page that is already there wins.

Without the `settings` handler the control is drawn, but the dialog does not know the field and cannot save it. Without the slot handler the field is saved, but no control changes it.

[#expected-result]
== Expected result

* The Writing Email page has a *Closing phrase* row after its built-in options.
* The built-in options of the page work as before.
* The value that you type is saved with *Save*, and it is still there after a reload.

[#if-it-did-not-work]
== If it didn't work

The control is not on the Writing Email page.::
* Cause: The Zimlet is not loaded, or the handler is registered under another slot name. The Modern UI does not check slot names, so a misspelled name adds nothing and shows no error. The name of this slot has two `t` in *writting*.
* Fix: Check that the sideloader shows the Zimlet as *Running*. Check the slot name in the xref:reference/slots.adoc[slot index] and that you register it in `init()`. Reload the page and open the dialog again.

The control is there, but the value is not saved.::
* Cause: The `settings` handler is missing, its `id` is not `writingEmail`, or the change did not go through `onFieldChange`. The dialog saves only the fields that it knows and whose value changed.
* Fix: Register `settings` with `id: 'writingEmail'` and the field. Report every change with `onFieldChange('closingPhrase')({ target: { value } })`, and build the value with `toProperty`, as the example does.

The control shows an empty field after you saved a value.::
* Cause: The `key` of the field differs from the `name` in the saved value. The dialog finds the saved value by name.
* Fix: Use the same name in the `key` of the field and in the `name` of the value, as `utils/fields.js` does.
