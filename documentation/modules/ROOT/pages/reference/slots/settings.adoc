= Settings

The Settings dialog is where users change their options. A xref:reference/glossary.adoc#zimlet[Zimlet] can add a section of its own with the `settings` key. It can also fill a slot to add a control to a page that the dialog already has. Use a section for options that your Zimlet owns. Use a slot for one control that belongs next to a built-in setting. To remove a built-in control, use the slots of xref:reference/slots/hide-built-in-ui.adoc#settings-dialog[Hide built-in UI].

[#before-you-register-a-handler]
== Before you register a handler

[#settings-dialog]
=== Settings dialog

The dialog has a list of pages at the left and the open page at the right. A section that you add with the `settings` key is another item in that list, after the built-in pages. A slot adds a control to a built-in page.

.The Settings dialog on the Writing Email page
image::slots-settings-dialog.png["The Settings dialog over the Mail screen, with the Writing Email page open. Outlined in red: the list of pages at the left, with General, Viewing Email, Writing Email and the other pages, and the block Composer of the open page with the font choices."]

The outlined list holds the pages of the dialog. The outlined *Composer* block belongs to the open page. A slot such as `writing-email-post-composer-settings` adds a control to a block like it.

[#saving-a-value]
=== Saving a value

A slot only draws a control. The dialog saves the value of a control only for a field that it knows. To save the value, register the `settings` key with the id of the built-in page and the field, as <<settings,`settings`>> describes:

[source,js]
----
plugins.register('settings', { id: 'writingEmail', fields })

// fields: { <field name>: { type, key, defaultValue? } }
----

The slots `writing-email-post-composer-settings`, `writting-email-additional-settings` and `calendar-and-reminders-video-call-preferences` pass `value` and `onFieldChange` for such a field. The `id` of their pages is `writingEmail` and `calendarAndReminders`. The other slots pass their own props. See their entries.

[#settings]
== settings

Adds a section to the Settings dialog, or adds fields to a section that the dialog already has. The key belongs to the whole dialog and not to one page.

[#settings-register-a-handler]
=== Register a handler

[source,js]
----
plugins.register('settings', settings)

// settings: { id, title, component, fields, afterSave?, hide? }
----

Pass the object itself, or a function that returns it. The dialog reads every object registered under the key.

[#settings-object]
=== Settings object

[[settings-id]]pass:[<a class="anchor" href="#settings-id"></a>]`id` (string)::
The name of the section, and the key of the values that the dialog passes to your component. Use an id that no other section uses. The id of a built-in section, such as `writingEmail`, adds your `fields` to that section instead of adding a section.

[[settings-title]]pass:[<a class="anchor" href="#settings-title"></a>]`title` (string or xref:reference/glossary.adoc#node[node])::
The name of the section in the list on the left. Always set it for a section of your own. A built-in section has a title already.

[[settings-component]]pass:[<a class="anchor" href="#settings-component"></a>]`component` (function `(props: object) => node`)::
The component that the dialog shows when the user selects the section. Its props are in <<settings-component-props,Component props>>.

[[settings-fields]]pass:[<a class="anchor" href="#settings-fields"></a>]`fields` (object)::
The values that the section saves. Each key is the name of a field, and each value describes the field, as <<settings-field,Field>> shows.

[[settings-after-save]]pass:[<a class="anchor" href="#settings-after-save"></a>]`afterSave` (function `(state: object) => void`, optional)::
Runs when the user chooses *Save*, after the dialog has collected the changed values and before it sends them. The dialog calls it on every save, whether or not the values of the section changed. It receives the state of the dialog.

[[settings-hide]]pass:[<a class="anchor" href="#settings-hide"></a>]`hide` (function `(props: object) => boolean`, optional)::
Leaves the section out of the list when it returns `true`. It receives the properties of the list, which include `accountData`, the account of the user.

[#settings-field]
=== Field

[[settings-field-type]]pass:[<a class="anchor" href="#settings-field-type"></a>]`type` (string)::
Where the dialog reads the value and where it saves it. Use one of these:
+
--
`modifyProperties`:: A property of the account that belongs to your Zimlet. The key is the name of the property.
`userPref`:: A user preference of the account. The key is the name of the preference.
`mailboxMetadata`:: An entry in the metadata of the mailbox. The key is the name of the entry.
`archiveMetadata`:: An entry in the archive metadata of the mailbox.
`userAttribute`:: An attribute of the account. The dialog reads it and does not save it.
`accountData`:: A field of the account. The dialog reads it and does not save it.
`whiteBlacklist`:: The lists of allowed and blocked addresses.
`filterRules`:: The mail filters.
`zimletPrefs`:: The preferences of the Zimlets of the account.
`desktopPrefLocal`:: A preference that the desktop app keeps on the computer. Other platforms do not save it.
--
+
A Zimlet that needs another type registers it with the `dynamic-settings` slot. See <<dynamic-settings,`dynamic-settings`>>.

[[settings-field-key]]pass:[<a class="anchor" href="#settings-field-key"></a>]`key` (string)::
The name under which the value is read and saved, as the type describes.

[[settings-field-default-value]]pass:[<a class="anchor" href="#settings-field-default-value"></a>]`defaultValue` (string, number, boolean, object or array)::
The value that the dialog shows when the account has no saved value.

[[settings-field-to-js]]pass:[<a class="anchor" href="#settings-field-to-js"></a>]`toJS` (function `(stored: unknown) => unknown`, optional)::
Turns the stored value into the value that your component reads from `value`.

[[settings-field-from-js]]pass:[<a class="anchor" href="#settings-field-from-js"></a>]`fromJS` (function `(value: unknown) => unknown`, optional)::
Turns the value of your component into the value that the dialog saves.

[#settings-component-props]
=== Component props

[[settings-prop-active-id]]pass:[<a class="anchor" href="#settings-prop-active-id"></a>]`activeId` (string)::
The `id` of the section.

[[settings-prop-value]]pass:[<a class="anchor" href="#settings-prop-value"></a>]`value` (object)::
The values of the fields of the section, by field name, after `toJS`.

[[settings-prop-on-field-change]]pass:[<a class="anchor" href="#settings-prop-on-field-change"></a>]`onFieldChange` (function `(fieldName: string) => (event: object) => Promise`)::
Reports a change. Call it with the name of the field, and call the function that it returns with an object whose `target.value` is the new value.

[[settings-prop-handle-validity-of-tabs]]pass:[<a class="anchor" href="#settings-prop-handle-validity-of-tabs"></a>]`handleValidityOfTabs` (function `(id: string, hasError: boolean) => void`)::
Tells the dialog whether the section holds a value that cannot be saved. Call it with `activeId` and `true` to disable *Save*, and with `false` to enable it again.

[[settings-prop-on-change-active-id]]pass:[<a class="anchor" href="#settings-prop-on-change-active-id"></a>]`onChangeActiveId` (function `(id: string) => void`)::
Opens the section with the given `id`.

[#settings-usage-notes]
=== Usage notes

* The dialog reads the registered objects when it opens, and again when a Zimlet registers one.
* Built-in sections come first. The sections of Zimlets follow in the order in which the Zimlets registered them. When two sections use the same new id, the dialog uses the first one.
* When `id` is the id of a built-in section, the dialog adds your `fields` to it and ignores `title` and `component`.
* When the user chooses *Save*, the dialog saves the fields whose value changed. A value that your component keeps to itself is not saved, so report every change with `onFieldChange`.
* For a complete example, see xref:build-by-goal/recipe-settings/new-section.adoc[Add a section to the Settings dialog] and xref:build-by-goal/recipe-settings/existing-section.adoc[Add a control to a built-in settings page].

[#dynamic-settings]
== dynamic-settings

Changes how the Settings dialog reads and saves values. Use it when a section needs a source of values, or a place to save them, that the built-in field types do not offer. To add fields to a built-in section, use it with the `settings` key.

[#dynamic-settings-register-a-handler]
=== Register a handler

[source,js]
----
plugins.register('slot::dynamic-settings', handler)

// handler: ({ onEditSettings, onAddZimletDataSource, onRegisterFieldTypeMethod }) => null
----

The Modern UI calls the handler as a function and draws what it returns. Register what you need inside it and return `null`.

[#dynamic-settings-props]
=== Props

[[dynamic-settings-on-edit-settings]]pass:[<a class="anchor" href="#dynamic-settings-on-edit-settings"></a>]`onEditSettings` (function `(sectionId: string, fields: object) => void`)::
Adds fields to the built-in section with the given `id`. The `fields` object has the same shape as the `fields` of the `settings` key.

[[dynamic-settings-on-add-zimlet-data-source]]pass:[<a class="anchor" href="#dynamic-settings-on-add-zimlet-data-source"></a>]`onAddZimletDataSource` (function `(key: string, load: (props: object) => Promise) => void`)::
Loads a set of values. The dialog calls `load` with its own props and keeps the object that the promise returns under `key`. A selector of a field type reads it from `zimletDataSources[key]` in its second argument.

[[dynamic-settings-on-register-field-type-method]]pass:[<a class="anchor" href="#dynamic-settings-on-register-field-type-method"></a>]`onRegisterFieldTypeMethod` (function `(name: string, methods: object) => void`)::
Registers a field type. `methods.selector(key, props)` returns the current value of a field of the type. `methods.updateAction(changed, props)` saves the changed values and returns a promise. The dialog converts the name to camel case, so `'SMX'` is the type `smx` in a field.

[#dynamic-settings-usage-notes]
=== Usage notes

* The Modern UI draws the slot once each time the dialog opens.
* `onEditSettings` does not change the first section, General. Pass the id of another section that exists.
* To use a type that you registered, set it as the `type` of a field. See <<settings-field-type,Field>> for the field keys.

[#additional-filter-settings]
== additional-filter-settings

Adds content in each filter of the Filters page and in the dialog that adds or edits a filter. Use it to mark reserved filters, which your Zimlet edits in a dialog of its own. Use it also to check the address of a redirect action.

[#additional-filter-settings-register-a-handler]
=== Register a handler

[source,js]
----
plugins.register('slot::additional-filter-settings', handler)

// handler: (props) => element | null
----

[#additional-filter-settings-props]
=== Props

The slot appears in two places, and the props differ. A prop that is in both places does not do the same thing.

[[additional-filter-settings-filter-rule]]pass:[<a class="anchor" href="#additional-filter-settings-filter-rule"></a>]`filterRule` (object)::
In a filter of the list only. The filter that the entry shows.

[[additional-filter-settings-shared-reserved-filter-data]]pass:[<a class="anchor" href="#additional-filter-settings-shared-reserved-filter-data"></a>]`sharedReservedFilterData` (function `(reservedFilters: object[]) => void`)::
In both places. Pass the list of reserved filters. Each object has `name`, `exactMatch`, `draggable` and `error`. A filter is reserved when its name is equal to `name`, or starts with it when `exactMatch` is `false`. In the list, `draggable` decides whether the user can move the reserved filter. In the dialog, a filter with a reserved name cannot be saved, and the dialog shows `error`.

[[additional-filter-settings-open-modal]]pass:[<a class="anchor" href="#additional-filter-settings-open-modal"></a>]`openModal` (boolean)::
In a filter of the list only. `true` after the user chooses to edit a reserved filter. The standard dialog does not open for it, so draw your own.

[[additional-filter-settings-set-open-modal]]pass:[<a class="anchor" href="#additional-filter-settings-set-open-modal"></a>]`setOpenModal` (function `(open: boolean) => void`)::
In a filter of the list only. Call it with `false` to close your dialog.

[[additional-filter-settings-trigger-update]]pass:[<a class="anchor" href="#additional-filter-settings-trigger-update"></a>]`triggerUpdate` (function `(filterRule: object) => void`)::
In a filter of the list only. Saves the filter that you pass in place of the filter that the user is editing.

[[additional-filter-settings-share-filter-validation-data]]pass:[<a class="anchor" href="#additional-filter-settings-share-filter-validation-data"></a>]`shareFilterValidationData` (function `(validations: object) => void`)::
In the dialog only. Pass an object with `isValidEmail`, a function `(address: string) => boolean`. The dialog uses it instead of its own check of the address of a redirect action.

[[additional-filter-settings-value]]pass:[<a class="anchor" href="#additional-filter-settings-value"></a>]`value` (object) and `onFieldChange` (function)::
In a filter of the list only. The values of the Filters page and the function that reports a change, as in <<filter-options,`filter-options`>>.

[#additional-filter-settings-usage-notes]
=== Usage notes

* The Modern UI calls the handler in each filter of the list and in the dialog. Pass the same list of reserved filters in each place.
